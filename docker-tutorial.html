01

What is a container, really?

Before any commands, the core idea — because everything else is downstream of it.

A container is your application plus everything it needs to run — the right version of Node, the system libraries, your built code, the settings — sealed into one standardized package. That package runs identically on your laptop, a coworker's machine, or a server in the cloud, because it carries its whole world with it.

ANALOGY

Before shipping containers existed, cargo was loaded loose — barrels, sacks, crates — each handled differently at every port. Then the world agreed on one standard steel box. Suddenly any crane, ship, or truck could move any box without caring what was inside. Docker is that standard box, but for software. The crane doesn't need to know if your box holds a Node app or a database — it just moves boxes.

Container vs. virtual machine

People often ask how this differs from a virtual machine. A VM ships an entire guest operating system for every app — gigabytes, slow to boot. A container shares the host's OS kernel and packages only what sits above it. Same isolation for most purposes, a fraction of the weight.

The container skips the biggest, heaviest layer — a whole guest OS per app.

Keep these three words straight

Dockerfile = the recipe (a text file). Image = the frozen result of following the recipe (read-only). Container = a running instance of an image. One image → many containers, like one class → many objects.

02

Why bother? From source to running box

The problem Docker solves is summed up in one sentence you've probably heard: "but it works on my machine."

Your app depends on a specific Node version, specific libraries, specific environment variables. If a teammate's machine differs even slightly, it breaks. Docker ends that argument by making the environment part of the deliverable. You don't ship instructions to recreate the setup — you ship the setup, already assembled.

What you install to follow along

Just one thing: Docker Desktop (Windows/Mac) or the Docker Engine (Linux). It gives you the docker command and a background service — the "daemon" — that actually does the building and running. Every command in this handbook talks to that daemon.

03

Reading the project before you build

You can't box up an app you don't understand. So the first real step is detective work: if I had a blank Linux machine, what would I need to do to run this app?

Let's answer that from the project itself. Fuzzie tells us what it needs if we look in the right files.

The clues, and what each one dictates

package.jsonUses Next.js 14 & Prisma → needs Node.js (we'll pick version 20). Its build script is next build.
next.configSets output: 'standalone' → Next produces a self-contained server we can ship without the giant dev toolchain.
prisma/schemaPrisma → we must run prisma generate at build, and the image needs the openssl system library.
/api/healthA tiny endpoint returning {status:"ok"} → perfect for a health check to prove the app is truly up.
.env filesSecrets like the database URL and auth keys → these are runtime config, never baked into the image.

The build recipe, in plain words

Translating those clues into steps a blank machine would run:

the manual version (what Docker will automate)
# 1. get Node 20 and the openssl library
# 2. install exact dependencies
npm ci
# 3. generate the Prisma client + engine
npx prisma generate
# 4. build the app (produces .next/standalone)
npm run build
# 5. start the generated server on port 3000
node server.js
The subtle one: two kinds of env var

Next.js freezes any NEXT_PUBLIC_* variable into the browser bundle at build time. Secrets (database URL, secret keys) are read at run time. This split decides where in the Dockerfile each value goes — remember it; we return to it in Chapter 05.

04

Deciding what to leave out

When you build, Docker copies your project folder to its engine — the "build context." Before writing the recipe, we tell it what not to send.

ANALOGY

Packing a suitcase for a trip, you don't throw in the whole house. You leave behind what you can buy at the destination (toiletries), what's private (your passport stays on you, not in checked luggage), and what won't fit anyway. A .dockerignore file is that packing discipline.

Create a file named .dockerignore next to your Dockerfile:

.dockerignore
node_modules
.next
.git
.env
.env.*
certificates
npm-debug.log*
README.md
Dockerfile

Each line earns its place for one of three reasons:

They're generated. We reinstall dependencies and rebuild inside the image on the correct OS. Worse, a node_modules built on Windows contains native binaries (Prisma's engine, image tooling) that simply crash on the Linux inside the container. Never copy them in.

They're secrets. An image is not a vault — anyone who has it can read every file inside. If your database password is baked in, it leaks with the image. We inject secrets when the container runs, not when it's built.

They're irrelevant to running. History, docs, and logs add weight and slow every build with no runtime benefit. Smaller context = faster builds and better caching.

The classic leak

Forgetting to ignore .env is the single most common security mistake beginners make. If you only remember one line in this file, remember that one.

05

Writing the Dockerfile, line by line

This is the heart of the handbook. A Dockerfile is a recipe read top to bottom. We'll build a multi-stage one — heavy work in throwaway stages, only the finished app in the image that ships.

ANALOGY

Think of a restaurant kitchen versus the plate that reaches the table. The kitchen has raw ingredients, mess, and tools — the build stages. The plate carries only the finished dish — the final image. Nobody sends the mixing bowls out to the diner. Multi-stage builds keep the kitchen out of the image.

The instruction cheat-sheet

FROM pick a base · WORKDIR set the folder · COPY bring files in · RUN execute at build time · ENV set an environment variable · ARG a build-time variable · EXPOSE document a port · USER drop privileges · CMD the default command when the container starts.

A single-stage build leaves everything in the final image: dev dependencies, the whole source tree, the compiler toolchain, caches — often well over a gigabyte. Every extra byte is download time and attack surface.

The deps stage installs packages. The builder stage compiles the app. The runner stage starts empty and copies in only the built server, its static files, and the Prisma pieces it needs at runtime. The first two stages are thrown away. Thanks to Next.js standalone output, the result is a fraction of the naive size.

Bind to 0.0.0.0, or it's unreachable

Inside a container, a server bound to localhost can only be reached from within that same container. Setting HOSTNAME=0.0.0.0 tells it to listen on all interfaces so Docker's port mapping can reach it from your machine. Skipping this is a top-five beginner frustration.

Checkpoint · Quiz 2

Where should the secret DATABASE_URL be placed?

Correct: secrets are runtime config. Baking them into the image (or copying .env) leaks them to anyone who has the image. We'll pass it with --env-file in Chapter 08.
06

Image layers & the magic of caching

Every instruction in a Dockerfile creates a layer — a saved snapshot of the filesystem changes it made. Understanding layers is what turns three-minute rebuilds into three-second ones.

ANALOGY

A layer is like a transparent sheet stacked on an overhead projector. Each instruction adds a new sheet on top. The final image is all the sheets viewed together. Crucially, Docker saves each sheet — so if a sheet hasn't changed, it reuses the saved one instead of redrawing it.

See caching in action

Here are the layers of our build. Press the buttons to simulate what Docker does. Watch which layers get CACHED (reused, instant) versus REBUILT (re-run).

Press "First build" to begin.

The golden rule of ordering

Put instructions that change rarely (installing dependencies) above instructions that change constantly (copying source code). Docker's cache is only valid until the first changed layer — everything below a change must re-run. That's exactly why we COPY package.json and install before we COPY . . the source.

Checkpoint · Quiz 3

You change one line in a React component and rebuild. What happens to the npm ci layer?

Exactly: because package.json is copied and installed before your source, editing a component doesn't invalidate the dependency layer. Only layers from COPY . . downward re-run.
07

Building the image

Recipe written. Now we run it. One command turns the Dockerfile into an image.

terminal — press Run
Press ▶ Run to simulate docker build.

Breaking that command down:

The verb: "read a Dockerfile and produce an image." It hands your build context to the Docker daemon, which executes each instruction in a temporary container and snapshots the result.

-t is tag — a human name for the image. Format is name:version. Without it you'd get an image identified only by a long hash, which is miserable to reference later.

The final . is the build context — the folder Docker sends to the daemon (minus your .dockerignore entries). It is not the path to the Dockerfile; Docker looks for ./Dockerfile by default.

Confirm the image now exists in your local library:

terminal — press Run
Press ▶ Run to list images.
Passing build-time public values

Remember the NEXT_PUBLIC_* split? Those are supplied at build with --build-arg, e.g. --build-arg NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_xxx. If omitted, the browser bundle bakes in a blank value and client features quietly break.

08

Running the container

An image is a frozen template. Running it brings a live container to life. This is where ports, environment variables, and volumes come in.

terminal — press Run
Press ▶ Run to start the container.

Ports: opening a door into the box

A container is isolated by default — nothing gets in or out. -p 3000:3000 publishes a port as HOST:CONTAINER. The left number is the port on your machine; the right is the port inside the container where the app listens.

ANALOGY

The container is a sealed warehouse. -p 3000:3000 installs a single labeled loading door connecting street-side door #3000 to interior dock #3000. Without it, the app is running but there's no door — localhost:3000 reaches nothing.

EXPOSE ≠ publish

The EXPOSE 3000 line in the Dockerfile only documents the port. It does not open it. The actual door is opened by -p at run time. New users mix these up constantly.

Environment variables: the runtime settings

Secrets and config are handed to the container as it starts. Best practice is a file, not a long chain of flags:

run with secrets
docker run -d --name fuzzie -p 3000:3000 --env-file .env.production fuzzie-app:local

-d runs it detached (in the background). --name fuzzie gives it a friendly handle. --env-file injects KEY=value lines as environment variables — this is how DATABASE_URL reaches the app without ever touching the image.

Volumes: keeping data alive

Containers are ephemeral — delete one and everything written inside vanishes. A volume is storage that lives outside the container's lifecycle, so data survives.

ANALOGY

The container is a hotel room; anything you leave in it is thrown out at checkout. A volume is a safety-deposit box at the front desk — it stays even after you leave and is there for your next stay. Databases always want a volume.

a database container with a volume
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16

-v pgdata:/path mounts a named volume pgdata at the folder where Postgres stores data. Destroy and recreate the container — the data is still there, in the volume.

Checkpoint · Quiz 4

Your app runs but localhost:3000 shows nothing in the browser. The most likely miss?

Most likely: the container is happily running, but without a published port there's no path from your machine into it. (A close cousin: the app bound to localhost instead of 0.0.0.0 inside the box.)
09

Living with your container

Day-to-day operation: see what's running, read logs, step inside, stop, remove, and rebuild after code changes.

What's running?

terminal — press Run
Press ▶ Run for docker ps.

docker ps lists running containers (add -a to include stopped ones). The STATUS column shows (healthy) once our health check passes — proof the app answers, not just that the process launched.

Reading logs — your first debugging move

terminal — press Run
Press ▶ Run for docker logs -f fuzzie.

docker logs fuzzie prints everything the app wrote to the screen. -f "follows" it live, like a security-camera feed. If a container crashes on startup, this is where the reason is.

Stepping inside a running container

terminal — press Run
Press ▶ Run for docker exec -it fuzzie sh.

docker exec runs a command inside a container that's already running. -it makes it interactive (a keyboard + a terminal), and sh opens a shell. Now you can ls around and confirm the files you copied really landed where you expect — the ultimate reality check.

Stopping, removing, rebuilding

Containers are disposable — you don't patch a running one, you replace it. The everyday loop after changing code:

the rebuild loop
# 1. stop and remove the old container
docker rm -f fuzzie
# 2. rebuild the image (fast, thanks to caching)
docker build -t fuzzie-app:local .
# 3. run the new one
docker run -d --name fuzzie -p 3000:3000 --env-file .env.production fuzzie-app:local
Why replace instead of update?

Immutability is the whole point. The running container always matches an exact, rebuildable image — there's no "well, I also hand-edited a file in there once." That reproducibility is what makes Docker trustworthy in production.

docker stop <name> — politely ask the app to shut down (sends a signal so it can clean up).
docker start <name> — restart a stopped container.
docker rm <name> — delete a stopped container (-f forces even if running).
docker rmi <image> — delete an image.
docker system prune — sweep up stopped containers and dangling images when disk fills.

10

When it doesn't work: debugging

Everyone hits these. Here's the diagnostic ladder and the usual suspects, each tied back to something we built.

First move: docker logs <name>. The startup error is almost always printed there — a missing environment variable, a database it can't reach, a typo in the start command. A container lives only as long as its main process; if that process dies, the container stops.

The background Docker service isn't running. On Windows/Mac, start Docker Desktop and wait for it to say "running." Every docker command talks to that daemon — no daemon, no Docker.

The static assets weren't copied. With Next.js standalone you must explicitly COPY the .next/static folder into the runner stage — the standalone bundle doesn't include it. Missing that line gives you an unstyled, JavaScript-less page.

The openssl system library is missing from the final stage, or the Prisma engine wasn't generated. That's why our Dockerfile installs openssl in the runner and runs prisma generate during the build.

You likely broke cache ordering — copying all source before installing dependencies makes every code edit reinstall everything. Reorder so package.json is copied and installed first (Chapter 06).

The universal debugging ladder

1. docker ps -a — did it even stay up? → 2. docker logs <name> — why did it stop? → 3. docker exec -it <name> sh — is the filesystem what I expect? Ninety percent of problems reveal themselves on these three rungs.

Proving it truly works

"Running" isn't "working." Verify in layers: docker ps should show (healthy); curl localhost:3000/api/health should return {"status":"ok"}; the browser should render the styled page; and a real action (sign-in, a dashboard load) confirms the database connection. Each rung tests a different layer of the stack.
